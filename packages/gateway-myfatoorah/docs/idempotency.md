# Idempotency

- **createPayment:** **requires** a caller `idempotencyKey`, sent as the `Idempotency-Key` header **only in KWT/SAU** (https://docs.myfatoorah.com/docs/idempotency — header is omitted elsewhere to avoid a validation rejection). MyFatoorah caches the key for **250 minutes** — replay `createPayment` with the same key after timeout / 5xx / `indeterminate` in KWT/SAU. The adapter does **not** mint a UUID. Create is auto-retried (`withRetry`) only in `KWT`/`SAU` (header dedupes, including `429`); KWT/SAU do **not** preflight `CustomerReference` by default (optional hardening below). Outside KWT/SAU `orderId` or `myfatoorahCustomer.reference` is **required** as the `CustomerReference` replay key, and create **first looks up** that `CustomerReference` via `POST /v2/GetPaymentStatus` (`KeyType: CustomerReference`, not unique — returns last invoice per https://docs.myfatoorah.com/docs/payment-inquiry and https://docs.myfatoorah.com/docs/get-payment-status) and reuses only a **Paid** invoice whose amount+currency match the request (MF-CREATE-REPLAY). `Pending`, `Refunded`/`PartiallyRefunded`, or a Paid invoice with a different amount/currency or missing amount are `indeterminate` with the existing `InvoiceId` when known (no second create); **`Canceled`/`Failed` (including `Expired` → `failed`) for the same `CustomerReference` allow a new `POST /v3/payments` only when no store fence blocks it** — a new invoice is created (retry after cancel/failure needs a reconciled fence; a fresh charge needs a **new** `CustomerReference` + key).

  **Store fence outside KWT/SAU (required):** `createPayment` requires a shared atomic `IdempotencyStore` (`config.idempotencyStore`) outside KWT/SAU. It is reserved **before** the `CustomerReference` inquiry + `POST /v3/payments`. The key is namespaced per account/country/mode/reference: `myfatoorah:create:<sha256(apiToken, country, live, CustomerReference)>`. A same-key replay with a different fingerprint throws (key reuse with different params); a `completed` reservation returns the cached response (including `PaymentURL` when available); `in_progress`/`unknown` reservations block (reconcile before retrying). Retain the reservation until reconciled — pre-submit failures delete it, post-submit `indeterminate` is stored as `unknown`, success is stored as `completed`.

  ```ts
  import type { IdempotencyStore } from "@paykernel/core";
  declare const callerStore: IdempotencyStore;
  const gateway = new MyFatoorahGateway(
    { apiToken, country: "ARE", idempotencyStore: callerStore },
    hooks,
  );
  ```

  Use a cross-instance production store with atomic `reserve()` (Redis `SET NX` / SQL unique constraint). `InMemoryIdempotencyStore` is single-process only (tests / one worker).

  **No automatic create POST retries outside KWT/SAU:** the `POST /v3/payments` runs once (`retry: false`; the headerless-validation fallback is the only single retry). Any transport error after `fetch` was invoked is potentially submitted (`afterProviderSubmit`) — reconcile via `GetPaymentStatus` + the store fence instead of re-POSTing blindly.

  **250-minute expiry (I5):** After **250 minutes** (https://docs.myfatoorah.com/docs/idempotency) the same `Idempotency-Key` creates a **new invoice** even in KWT/SAU — the dedupe window has expired and KWT/SAU do not preflight `CustomerReference` by default. For post-expiry safety **also pass a stable `orderId` (`Customer.Reference`) even in KWT/SAU** and **retain the `idempotencyKey` server-side until settlement** (`Paid` via webhook or `GetPaymentStatus`). Optional hardening (see `local://replay-proposal.md`, best-effort, never blocks create): after expiry, if a `CustomerReference` lookup finds `Paid`+amount+currency match, reuse it even in KWT/SAU; otherwise fall through to `POST` without blocking on `Pending`/mismatch/`5xx`/`429`. At minimum, do not reuse an `orderId` for a new charge until the prior invoice is settled or you intentionally want a new invoice with a **new** `orderId`.

  **Rate-limit on lookup (I2):** The replay `GetPaymentStatus` itself is rate-limited (official warning on https://docs.myfatoorah.com/docs/get-payment-status). A `429` on that lookup is surfaced as `RateLimitError` (with `Retry-After`) so callers can back off and retry the same `orderId`/`idempotencyKey` without creating a second invoice. Other lookup failures (`5xx`, non-404 `4xx`, `IsSuccess:true` with empty `Data`) remain `indeterminate` with the existing `InvoiceId` when known. See [Charges](./charges.md#rate-limit-on-replay-lookup-i2) and `local://replay-proposal.md`.

  **Pending URL recovery (I1):** `GetPaymentStatus` has no `PaymentURL` and `GET /v3/invoices/{id}` returns `"No invoices match this InvoiceId"` when there are no transactions (official). A provider-pending invoice without a cached result cannot have its redirect recovered via inquiry — persist `PaymentURL` before ACK (outside KWT/SAU the completed store reservation persists it when available); after a crash without a cached result, query status but the redirect is lost, so create a new `orderId` for a new invoice. The adapter's pending case returns `indeterminate` with the existing `InvoiceId` (no second create) except `Canceled`/`Failed` which allow new subject to the store fence above. See [Charges](./charges.md#pending-paymenturl-recovery-limit-i1).

- **refundPayment:** requires `idempotencyKey`, sent as `ExternalIdentifier` and (best-effort) the `Idempotency-Key` header **only in KWT/SAU**. A “header not supported” validation error retries **once** without the header (`retry: false` — no 429 fan-out). The **first** `MakeRefund` also does **not** auto-retry `429` (`isMyFatoorahRetryableBeforeSubmit` excludes `RateLimitError`). Conflicts are not retried. `ExternalIdentifier` still carries the key for replay. `MakeRefund` is **not** auto-retried after submit (`afterProviderSubmit`), because `ExternalIdentifier` does not dedupe on the gateway: reconcile via `GetRefundStatus` + the nested-refund key match instead of a second `POST` (preflight). Transport failures after `fetch` was invoked are potentially submitted. **Any existing refund with `ExternalIdentifier === idempotencyKey` is returned immediately (idempotent partial-refund replay via `GetRefundStatus` preflight — MF-CREATE-REPLAY style `ExternalIdentifier` + `GetRefundStatus`) — `MakeRefund` is never re-POSTed, even when `remaining > 0`.**

  **Concurrent refunds (I6):** `ExternalIdentifier` is **not provider-deduped** and the `GetRefundStatus`→`MakeRefund` sequence has a TOCTOU window. Two parallel `refundPayment` calls with different keys can each observe the same `remaining` and both `MakeRefund` (double-refund outside KWT/SAU). KWT/SAU `Idempotency-Key` only dedupes the HTTP window, not `ExternalIdentifier`. **Require a caller-side distributed lock per `InvoiceId` (or per `orderId`) for `refundPayment` outside KWT/SAU** — see [Production checklist](./production-checklist.md) and [Refunds](./refunds.md). The adapter's preflight `GetRefundStatus` by `ExternalIdentifier` prevents duplicate posting for the **same** key (crash-retry safe), but not concurrent different keys.

- Replay protection: a fully refunded invoice maps **only** the nested refund whose `ExternalIdentifier` exactly matches the key; otherwise it throws — never re-POSTs the invoice amount and never maps a single unkeyed refund to an unrelated key. Partial-refund replays with the same key also map to the existing refund before posting. Inquiry `POST`s (`GetPaymentStatus` / `GetRefundStatus`) are not money-mutating. `SR`/`KD` and dotted variants `S.R.`/`K.D.` aliased to `SAR`/`KWD`; grouping commas stripped. Create outside KWT/SAU uses the `CustomerReference` lookup above instead of header dedupe. `InvoiceValue` is **base currency** per https://docs.myfatoorah.com/docs/get-payment-status; fixtures use KWD base + SAR pay.

- **Aborts:** a pre-aborted caller `signal` fails before any HTTP (`PaymentAbortedError`, no fetch, no post-submit marking) on every operation. An abort racing an in-flight mutating `fetch` maps to `NetworkError(afterProviderSubmit)` — reconcile, do not assume unsubmitted.
